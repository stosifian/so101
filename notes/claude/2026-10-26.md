## Surprises
- **Goal_Position = 0, Goal_Speed = 0 (unlimited), Acceleration = 0 (unlimited) at power-up.** Naively writing Torque_Enable=1 would let a joint drive toward tick 0 at full speed. The safety layer must set goal := present and cap speed/accel *before* enabling torque. The spec didn't anticipate this.
- **Seeed already wrote homing offsets to EEPROM** (non-zero `Offset` on all 12 servos), so `Present_Position` is already offset-corrected out of the box. Running LeRobot calibration would overwrite these, which is why the spec says to dump before and after.
- **No firmware angle limits** (0..4095 everywhere). Software limits are the only guard.
- Leader shoulder_lift (ID 2) has a different EEPROM fingerprint from the other leader servos (Phase 12 vs 92, Max V 8.0 vs 12.0, Protection_Current 500 vs 300). It's the one leader joint with 1/345 gearing, matching the follower. **Correction:** Model is identical, but the gear variant *is* distinguishable via EEPROM config.
- Both driver boards enumerate as identical CH343 devices (`1a86:55d3`, product 'USB Single Serial'). Only the board serial in the device name distinguishes them, so the mapping has to be recorded rather than guessed.
- A board can enumerate perfectly with its servos dead to the bus: USB powers the bridge chip, not the servos. "Port exists" ≠ "arm is reachable".
- The existing anaconda base Python is **x86_64 under Rosetta** (3.9.19), as is the `shoggoth` env. On an M1 that means slower numerics and possible wheel mismatches, so this project uses a fresh native arm64 env via uv.
- `serial.tools.list_ports.ListPortInfo` isn't exposed on the macOS build of pyserial 3.5. The class lives in `serial.tools.list_ports_common`.

- **`import so101` failed under pytest and `uv run`.** Root cause: the Desktop is iCloud-synced ("Desktop & Documents"). iCloud sets the macOS `UF_HIDDEN` flag on files inside dot-folders within ~1 s (reproduced with `.hidtest/a.pth`). **Python 3.12.15's `site.py` skips hidden `.pth` files** (site.py:176), so the editable install's `_editable_impl_so101.pth` is silently ignored. It worked at Step 0 only because the import beat iCloud. This is very likely the true root cause of shoggoth LESSONS_LEARNED #3 as well (also on ~/Desktop).

- **Single-sample telemetry glitches on the leader** (run 20261026-121107_telemetry_both, 3 s at 100 Hz, both arms polling): wrist_roll had 5/307 outlier samples (V 4.2/4.4/4.8/5.0, T 27–33 °C vs a steady 4.9 V / 26 °C), wrist_flex 1–2, gripper 1. These packets passed the checksum, so the values are wrong rather than the read failing. They're physically impossible (+7 °C for one 10 ms sample). Only downstream leader servos are affected; follower clean. **Follow-up (30 s runs + A/B test):** it also happens with leader-only polling, and on the follower. On both arms it's always **IDs 4–6** (wrist_flex 0.2–0.7 %, wrist_roll 0.7–1.2 %, gripper 0.7–1.6 % of samples); IDs 1–3 are clean. Voltage only reads low (down to 3.6 V on 4.9 V, 10.4 V on 11.9 V) and temperature only high (up to +11 °C). Glitches on different joints don't coincide, so it isn't a supply dip. The rest of the packet is normal. A/B on the follower, alternating the 15-byte block read with per-register reads (3000 rounds), gave the same rates, and in the same round both methods returned **identical glitched values** ~1 ms apart. So the glitched value really sits in the servo register briefly: **servo-side ADC noise, not our read path.** Hypothesis for IDs 4–6: end-of-chain wiring/ground. **Consequences:** step 4 temp/voltage trips must debounce (N consecutive samples or a median); raw logs stay raw; Phase 2 thermal analysis median-filters temperature.

- **Rerun viewer launch stalls the pollers** (step 3e, run 20261026-124805_telemetry_both): between 1.0 and 1.4 s after start, reads went up to 33 ms with 3–4 skipped slots per arm; the rest of the run was clean. With the viewer already open (20261026-125012) timing matched no-viz runs (2–3 overruns, max ~12 ms). Fix: a 2 s settle after spawn. Rule for step 4+: start the viewer before torque-on, never mid-motion.
- `Present_Speed` goes nonzero when a joint is back-driven by hand (confirmed by user, step 3d).

- The follower's **rest pose sits outside its own margined limits** (elbow_flex at its stop 2927 > 2878; closed gripper ~2045 < 2082). LeRobot never meets this because its limits equal the swept extremes. SafeArm must allow starting outside the range.
- **The Rerun viewer kept the previous run's layout:** with `set_sinks(default_blueprint=...)`, a viewer left open from a leader run showed nothing for a follower run. Fixed with `send_blueprint(make_active=True)`. Ctrl-C also reaches the spawned viewer and kills it, so `viz.close()` is now best-effort (it crashed shutdown once; parquet was unaffected).

- **Replaying real telemetry through the trip checker found a false trip before any hardware test:** the leader gripper's Status register reads 0x01 (voltage) on 27 of ~264k samples, always the same samples where its voltage ADC glitches below the servo's own 4.0 V floor. A "trip at once on any Status bit" rule would have tripped on noise. Voltage/overheat bits are now debounced; overload/overcurrent/angle stay immediate. Good argument for replay tests on recorded data.

- **Step 5a (shadow mode on the real follower) passed:** run 20261026-142826_shadow_follower, 60 s at 100 Hz, 5,957 cycles, **0 write attempts, no trips** on live data (ADC glitches included), 0 drops. Side findings: 3 failed reads (IDs 4–6 only), each stalling the loop ≤ ~100 ms via the SDK timeout; 42 reads > 8 ms not correlated with hand motion (likely TUI/Rerun in-process). Median read 3.1 ms, median period 9.99 ms, p99 13.4 ms.

- **Step 5b (first torque-on) passed:** run 20261026-144830_hold_follower: enable took 20 ms for 6 joints, **0 ticks of motion at torque-on**, 20 s hold, no trips, torque off confirmed. Load/current 0 at rest (the folded arm sits on its stops, so nothing to hold up). Push test 20261026-145026_hold_follower: shoulder_pan resisted (≤ 9 ticks under a hand push, load ≈ 0.85 %/tick, sprang back), proving torque was physically engaged, not just set in the register. The hold loop showed 112 overruns / 18 skipped in 30 s with 0 read failures (TUI cost suspected; compare without the TUI at 5c).

- **Step 5c (first commanded move) passed:** run 20261026-145837_move_follower, shoulder_pan +100 ticks @ 50 ticks/s ×2, no trips/clamps/failures, other joints 0 ticks. Tracking lag 5 ticks, no overshoot, settle 30–80 ms, **0 jitter at hold (P=32)**, steady-state error −1 (upward) / +2…+3 (downward). `Moving` drops to 0 while still 1–3 ticks off. **Step 5 done.**

- **Stick-slip experiment (5d):** the user saw stair-stepped motion at 50 ticks/s. Data: friction stick-slip (breaks free at 5–8 ticks of error, dead zone 1). Stream 150 t/s cut the stuck share from 51 % to 12 % (lag 20 ticks, load 6.4 %); letting the servo's own profile run at 50 t/s made it worse (57 %, 200 ms stalls). Smoothness comes from speed, not from who plans the trajectory.

## Decisions (+why)
- **FK+IK in Phase 1** (the spec deferred it). It's built as a *parameterized* model so the same code becomes the Phase 2 kinematic-calibration model.
- **Bypass LeRobot** for servo I/O (spec §4) and use `scservo_sdk` directly. LeRobot normalization and calibration hide raw ticks and may write EEPROM.
- **Motion safety by structure:** motion-capable scripts live in `scripts/motion/` behind a permission prompt plus a `--arm-moves` flag. Read-only scripts never touch torque or goal registers.
- **Rerun for live viz:** it records `.rrd` files that can be replayed, it handles time series and 3D in one viewer, and LeRobot already uses it. Parquet stays the canonical analysis data.

- **One owner per bus per session (option C, chosen over a command queue to the poller thread or a shared lock).** The poller is for read-only sessions only. From step 4, SafeArm's synchronous loop owns the follower bus (read → check → write → publish to hub), which is LeRobot's loop shape. Why: scservo_sdk is request/reply on one serial line, so concurrent use can cross replies. C makes that impossible by construction, keeps the multi-step torque-enable sequence indivisible, and keeps concurrency out of the motion path. Enforced with `bus.claim()/release()` (BusError on a second claim). Safety checks run inline in the owner loop, not as a hub consumer, because hub queues drop samples by design.

- **Copy LeRobot patterns unless a hard rule forbids it** (added to CLAUDE.md). Why: tested on real hardware, and it limits invention (the shoggoth problem). Conditions: cite file + commit, note what changed and why. LeRobot-derived code stays behind our own interfaces so Phase 2 can go beyond it piece by piece. The Phase 2 caveats are listed in ROADMAP.

- **Parking = stop at the soft limit, then torque off** (user, option 1 of 3). The elbow's rest pose (2927) is outside its limit (2878), and once inside its range a joint can't leave it, so a return-to-rest stops ~4.4° short. At torque-off the elbow settles the rest onto its stop under gravity. Rejected: a special park move that may pass the limit (code at the riskiest edge), and a zero elbow margin (commands could reach the hard stop).
- Upstream LeRobot (huggingface/lerobot @ 45cca1a) checked for step 4: `SOFollower.configure()` writes PID, Return_Delay, Acceleration=254 and Phase (EEPROM) on every connect, and would rewrite the leader's Phase (92 has bit 4 set). Its `enable_torque` doesn't sync goal in Python, `max_relative_target` defaults to None, and it now uses the `rustypot` backend instead of scservo_sdk. We keep scservo_sdk (user decision) behind `ServoBus`.

- **Motion default: streamed ramps at ~150 ticks/s** for smooth motion (step 5d data). Accept stick-slip on slow precision moves and measure at settled stops with controlled approach direction. P/I tuning (EEPROM) shelved unless step 6 shows a need.

- **Keep P=32** (factory; LeRobot writes 16). Step 5c/5d: 0 holding jitter, and stick-slip depends on speed, not P; P=16 would roughly double the breakaway error. No EEPROM write.

## Open questions
- **Present_Current scale unverified:** during the 5b push it read 1–4 units (6.5–26 mA at the assumed 6.5 mA/unit) at ~8 % load, roughly 8× below a rough stall-current estimate (~2.7 A × 8 %). Treat current as relative until checked against the PSU's ammeter (5c move) or the step 10 gripper squeeze.
- Loop stalls up to ~100 ms when a wrist servo misses a reply (SDK timeout ~34 ms per attempt, 2 retries). Safe (servo keeps its last goal), but consider a shorter timeout or fewer retries before step 6 timing-sensitive sweeps. Also check the wrist cabling (IDs 4–6 glitch and drop replies).
- SimBus has no acceleration profile, so simulated speed is a 0/200 square wave. Offered to add an accel limit (~20 lines); real firmware profile only known at step 5c.
- `Moving` (reg 66) stays 0 while a joint is back-driven by hand with torque off; Present_Speed is the hand-motion signal. It seems to mean "commanded move in progress", not "shaft turning" (not confirmed in Feetech docs). Verify under torque at step 5 before `wait_until_settled()` relies on it.
- Lower P from 32 to 16 like LeRobot? **Step 5c: 0 ticks holding jitter at P=32 (no load). **Decided: keep P=32 for now (user, 2026-10-26; no EEPROM write). Recheck under gravity load at step 6.**
- Set firmware angle limits as a second safety net (EEPROM write), or keep limits software-only? Decide at step 4.
- Is the USB hub powered, and are both boards going through it?

## Write-up hooks
- The "hidden .pth" story: two individually reasonable behaviours (iCloud hiding dot-folder files; Python skipping hidden .pth files) combining into a silent import failure that had already bitten the previous project.
- "Read before you write": the factory register dump showed the arm would lunge on naive torque-enable. A case for dumping state before the first command.
- Diagnosing a silent leader by elimination: USB enumerates → ping scan across all bauds/IDs is empty → therefore physical → it was the driver→motor cable. A clean example of narrowing layer by layer.
- "Architecture for a project whose phase 3 is unknown": one telemetry stream with many consumers, and one run format from day 1.
